## Protocol

Perform all steps in order without asking the user questions. Pauses are allowed
only in Step 8 (waiting for the next round).
The only source of truth is the files in:

```text
{{SESSION_DIR}}/
```

Do not delete or overwrite anything inside the session. Add new files only.

### Step 1. Check the round state

Expected files for the current round:

```text
{{ROUND_ID}}-01-round-start.md
{{ROUND_ID}}-02-claude-claimed.flg
{{ROUND_ID}}-03-claude-review.md
{{ROUND_ID}}-04-codex-claimed.flg
```

Rules:

- if `{{SESSION_DIR}}/final.md` already exists, stop without messages;
- if `{{ROUND_ID}}-03-claude-review.md` already exists, validate it through
  `{{PROTOCOL_SCRIPT}}` with `-Kind claude-review -ValidateOnly`, then resume
  Step 8 for this round; an existing review is not completion of the session;
- if `{{ROUND_ID}}-01-round-start.md` does not exist, verify that fact in the
  filesystem first, then stop.

### Step 2. Claim the round

Run:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "{{PROTOCOL_SCRIPT}}" -SessionDir "{{SESSION_DIR}}" -RoundId "{{ROUND_ID}}" -Kind claude-claim
```

`status: created` and `status: already_exists` are both success. The latter
means the round was claimed earlier and this run may be recovering from an
interruption. On `status: error`, stop and report the returned reason. Do not
create or rename the sentinel manually.

### Step 3. Read the context

Read `{{ROUND_ID}}-01-round-start.md`. It contains a JSON block (machine-readable
round fields) followed by prose (review context).

From the JSON block, take:

- `round` — the round number;
- `scope` — the review scope (the same for every round in the session);
- `session_id` — for reference.

From the prose, take:

- `## Context` — what the task is and where it stands;
- `## Task` — what to check;
- `## Files` — what to read;
- `## Special notes` — what to pay particular attention to;
- for rounds 2+, also `## What changed since the previous round`,
  `## Accepted Issues`, and `## Rejected Issues`.

The review-quality contract is shared by all sessions; see `## Rules` below in
this prompt. It is not repeated in round-start.

Additional interpretation rules:

- `{{ROUND_ID}}-01-round-start.md` is the contract for the current round and a
  summary of changes already made; it is not a replacement for the real files
  listed in `## Files`;
- if `What changed since the previous round` or `Accepted Issues` says that a
  plan, code, or document was updated, still read the corresponding file from
  `## Files` yourself;
- if the summary in `{{ROUND_ID}}-01-round-start.md` disagrees with the actual
  file contents, the file itself remains the source of truth for evidence, and
  the discrepancy is a valid finding.

### Step 4. Study the code

Follow the reviewed project's code-navigation rules. If a tool required by those rules is unavailable, report the limitation; this bundle itself does not require Serena.

Read every file listed in `## Files`.
Read each file completely; do not guess its contents.
If a file is missing or unreadable, do not guess. Record it as a separate
finding in the review file with its path, then continue to the next file.

Review scopes:

- `plan-only` — code has not changed; review the quality of the plan;
- `production-change` — code has changed; review the actual code;
- `lookup-test` — verify a hypothesis or API;
- `architecture-check` — review an architectural decision.

### Step 5. Conduct the review

Act as an independent senior reviewer.

**Review-quality contract (applies to every round):**

- review only the declared scope (`scope` from round-start);
- report only significant findings;
- support every finding with code, plan text, or verifiable logic;
- do not report stylistic nitpicks, weak hypotheses, or “would be nice” ideas;
- explicitly check for missed requirements, regression risks, and over-engineering.

**Severity levels (`severity`):**

- `critical` — bugs, data loss, or security issues;
- `major` — architectural mistakes or missed requirements;
- `minor` — style, naming, or small improvements.

**Finding fields in the JSON block** (see the Step 6 template):

- `severity` — one of the levels above;
- `confidence` — integer 75–100 expressing confidence in the finding;
- `evidence_path` — a path with forward slashes `/`, relative to the project
  root or absolute;
- `evidence_anchor` — a method/function name for code, or a section/heading for
  text; include line numbers only when actually verified;
- `summary` — a short finding title.

Put the detailed reasoning (Problem / Impact / Proposal) in the prose section
under `### Finding N: <summary>`, not in JSON.

If context is insufficient:

- do not ask the user directly;
- do not create separate service files;
- record the missing context as a finding in the review, with a clear question
  or list of missing data.

### Step 6. Write the result

Prepare the complete review in a uniquely named temporary file outside
`{{SESSION_DIR}}`. Do not create the canonical review file directly. Publish
the draft through this command:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "{{PROTOCOL_SCRIPT}}" -SessionDir "{{SESSION_DIR}}" -RoundId "{{ROUND_ID}}" -Kind claude-review -ContentPath "<absolute_temp_review_path>"
```

The script derives the canonical name, validates the heading and JSON contract,
checks the round and scope against round-start, validates all finding fields and
prose sections, and creates the canonical file atomically. Continue only on
`status: created` or `status: already_exists`. On `status: error`, fix the
temporary draft and run the command again. Never overwrite an existing
canonical file.

The file has two parts: a fenced JSON block (the machine-readable source of
truth for the initiator) and prose below it (the human report). The JSON block is
required and must be the first content after the heading
`# Claude Code review for round N`.

Use this template. The outer fence has four backticks so the nested ```json
fence remains literal. In the actual `R<N>-03-claude-review.md`, write the JSON
block with the normal three backticks:

````md
# Claude Code review for round N

```json
{
  "round": N,
  "verdict": "NEEDS_WORK",
  "scope": "<value from round-start>",
  "summary": "Short review summary in 1–3 sentences.",
  "findings": [
    {
      "id": 1,
      "severity": "major",
      "confidence": 85,
      "evidence_path": "path/to/file.bsl",
      "evidence_anchor": "method MethodName",
      "summary": "Short finding title"
    }
  ]
}
```

## Summary
Prose summary in 1–3 sentences.

## Findings

### Finding 1: <same text as `findings[0].summary`>

Problem:
Briefly state the issue.

Impact:
Explain the consequence: bug, regression, missed requirement, over-engineering,
and so on.

Proposal:
State what should change.
````

When there are no findings:

- use `verdict: "APPROVED"`;
- use `findings: []` (an empty array);
- leave `## Findings` with the text “None.” instead of adding `### Finding 1`.

Canonical JSON values:

- `verdict`: `APPROVED` | `NEEDS_WORK` | `REJECTED`
  - `APPROVED` — no findings; the material is ready;
  - `NEEDS_WORK` — findings require fixes before approval;
  - `REJECTED` — use rarely, only when the fundamental approach is wrong and
    continuing the review in its current direction is pointless;
- `scope`: `plan-only` | `production-change` | `lookup-test` | `architecture-check`;
- `severity`: `critical` | `major` | `minor`;
- `confidence`: integer 75–100;
- `id`: integer, starting at 1 and consecutive within the round;
- `round`: integer (the number without the `R` prefix).

Use forward slashes `/` only in JSON paths. Backslashes `\` break
`ConvertFrom-Json` because they are JSON escapes. Relative paths from the project
root are preferred; absolute paths with forward slashes such as `c:/1C/...` are
also valid. Dots in directory names and extensions are safe.

The prose below the JSON is for humans. You do not need to repeat
`summary`, `severity`, or `evidence_path` in prose, but you must provide the
detailed Problem / Impact / Proposal explanation for every finding under
`### Finding N: <summary>`.

### Step 7. Report the round result

After the protocol script publishes `{{ROUND_ID}}-03-claude-review.md`, send one
short, substantive message to the chat:

- heading `**Раунд N**`;
- `verdict`;
- 1–3 key conclusions from the round.
- make the message directly visible; do not hide it in `<details>` or another
  collapsible container;
- after that message, immediately continue to Step 8 in the same run; do not
  wait for a user reaction or end the protocol at the `**Раунд N**` message.

### Step 8. Wait for the next round

Start one silent wait process:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "{{WAIT_SCRIPT}}" -SessionDir "{{SESSION_DIR}}" -RoundId "{{ROUND_ID}}" -WaitFor next-or-final -TimeoutSec 0
```

`TimeoutSec 0` means no deadline. The script, not the agent, owns the polling
and checks for both the next round and `final.md`. Do not track elapsed time,
create timeout flags, or stop merely because an hour has passed.

If the shell returns a running-session handle without JSON, keep polling that
same shell session. When JSON with `status: ready` arrives:

- `event: final` — go to Step 9;
- `event: next` — set `ROUND_ID` to the returned `next_round` and return to
  Step 1.

If the shell process is interrupted without terminal JSON, inspect the two
expected files. Continue from the file that exists; if neither exists and the
wait process is confirmed terminated, restart the same wait command once as
recovery. Do not launch another reviewer.

### Step 9. Report the overall session result

If `final.md` appeared during this run's wait loop:

- read `{{SESSION_DIR}}/final.md`;
- send one short, substantive message with heading `**Итог ревью**`;
- include the final session status and 1–3 overall conclusions;
- make it directly visible; do not hide it in `<details>` or another collapsible
  container;
- then stop.

If `final.md` already existed before this run and no new round was processed,
stop silently.
