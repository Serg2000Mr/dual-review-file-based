# Codex Dual Review (File-Based)

Текущий чат — инициатор; другой выбранный чат — независимый проверяющий. Это могут быть любые агенты, включая Codex → Codex и Codex → ZCode. Название навыка, заголовки рецензий и части имён файлов codex/claude — обозначения протокола для совместимости, а не ограничения выбора агента.
Source of truth — только файлы в `<SESSION_DIR>/`.

## Пути и рабочие деревья Git

`SESSION_DIR` — абсолютный путь к каталогу сессии. Вычислить его как `<PROJECT_ROOT>/.dual-review/<session_id>`, где `PROJECT_ROOT` — текущий корень проекта Claude Code. Если Claude Code запущен внутри отдельного рабочего дерева Git, именно оно является `PROJECT_ROOT`; не переносить сессию в основной checkout.

Каталог вспомогательных файлов навыка (`SKILL_DIR`) — каталог, содержащий этот `SKILL.md`. Брать `reviewer-prompt.txt` и скрипт ожидания из него, а не строить путь относительно `PROJECT_ROOT`.

Передавать Codex абсолютные `SESSION_DIR` и `REVIEWER_PROMPT_PATH`. В тексте промпта и JSON использовать прямые слеши `/`.

## Invocation

```
/codex-dual-review-file-based <описание задачи> [путь/к/плану.md] [max_rounds=5]
```

Если путь к плану передан — прочитать его и использовать как основу `round-start`.
Если `max_rounds` не указан — по умолчанию 5.

## Файловый контракт

- Внутри одной сессии только добавляются новые файлы. Append-only.
- Протокольные файлы не удаляются и не перезаписываются.
- Состояние раунда определяется листингом каталога: `.flg`-файлы — это zero-byte sentinel и часть state machine, не «шум».
- `R*-02-codex-claimed.flg` означает, что Codex забрал раунд; `R*-04-claude-claimed.flg` — что Claude завершил обработку review-файла, включая возможную фиксацию ошибки его контракта. Это сигнальные файлы состояния, а не признак того, что агент сейчас выполняется.
- Область ревью (`scope`) фиксируется в первом раунде и не меняется в пределах одной сессии.
- `final.md` означает, что сессия завершена.
- Если в новом round-start заявлено, что план, код или документация уже обновлены, эти изменения должны реально существовать в перечисленных файлах до публикации `R<N>-01-round-start.md`. Поля `Что изменилось с прошлого раунда`, `Accepted Issues` и `Rejected Issues` фиксируют уже принятые решения и уже внесённые изменения, а не TODO на потом.

Правила интерпретации round-start reviewer-ом — в `reviewer-prompt.txt`, Шаг 3.

## Алгоритм

### Шаг 1. Подготовить контекст раунда

Изучить кодовую базу. Подготовить контекст для ревью:
- что именно нужно проверить;
- какие файлы относятся к задаче;
- какой `scope` нужен.

Канонические значения `scope`:
- `plan-only`
- `production-change`
- `lookup-test`
- `architecture-check`

Правило выбора:
- если описываются будущие изменения — `plan-only`;
- `production-change` допустим только когда код уже изменён.

### Шаг 2. Создать сессию и зафиксировать абсолютный SESSION_DIR

Если пользователь не дал `session_id`, создать новый в формате `YYYYMMDD-HHMMSS-SSS`.

Зафиксировать абсолютные пути до создания первого протокольного файла:

```text
PROJECT_ROOT         = текущий корень проекта Claude Code
SESSION_DIR_ABS      = <PROJECT_ROOT>/.dual-review/<session_id>
SKILL_DIR            = каталог, содержащий этот SKILL.md
REVIEWER_PROMPT_PATH = <SKILL_DIR>/reviewer-prompt.txt
WAIT_PS1_PATH        = <SKILL_DIR>/wait-for-review.ps1
WAIT_SH_PATH         = <SKILL_DIR>/wait-for-review.sh
```

Не искать `SKILL_DIR` относительно `.claude/skills`: навык может быть установлен глобально, через символическую ссылку или в другом поддерживаемом каталоге.

Перед созданием сессии проверить:

```bash
test -f "<SKILL_DIR>/reviewer-prompt.txt"
test -e "<PROJECT_ROOT>/.git"  # для Git-проекта: каталог в обычном checkout, файл в worktree
```

Если вспомогательный файл отсутствует — остановиться: навык установлен не полностью. Если это Git-проект и `.git` отсутствует, остановиться и попросить перейти в корень нужного checkout или рабочего дерева. Для проекта без Git проверить его известный корневой файл или каталог; не искать корень эвристически.

Создать каталог `SESSION_DIR_ABS`. Все последующие операции с протокольными файлами идут только по нему.

### Шаг 3. Открыть раунд (единый шаблон для R1 и R2+)

Создать файл `<SESSION_DIR>/R<N>-01-round-start.md`. Файл состоит из двух частей: JSON-блок в fenced-секции (машинно-читаемые поля раунда) и проза ниже (контекст для reviewer-а).

Единый шаблон. Внешний fenced-блок открывается четырьмя backtick'ами, чтобы вложенный ```json остался внутри. В реальном файле сессии `R<N>-01-round-start.md` JSON-блок пишется обычными тремя backtick'ами:

````md
# Раунд N

```json
{
  "round": N,
  "scope": "plan-only",
  "session_id": "20260502-103015-001"
}
```

## Контекст
Коротко: что это за задача и какой результат ожидается (для R1) или где мы находимся после прошлого раунда (для R2+).

## Задача
Что именно должен проверить reviewer.

## Файлы
- path/to/file1
- path/to/file2

## Особые замечания
Что важно не упустить именно в этом раунде.
````

Условные секции (только для R2+, после первого раунда):

````md
## Что изменилось с прошлого раунда
Только уже внесённые изменения в перечисленные выше файлы. Не обещания и не TODO.
- ...

## Accepted Issues
- F1 — суть, как исправлено
- F3 — суть, как исправлено

## Rejected Issues
- F2 — аргумент: файл, метод, логика
````

В `Accepted Issues` / `Rejected Issues` достаточно ссылки на `id` finding из `R<N-1>-03-codex-review.md` (`F1`, `F2`, ...) и одной строки решения. Не цитировать прозу замечаний целиком — она уже есть в предыдущем review-файле.

**Канонические значения JSON-полей:** см. Шаг 6 reviewer-prompt.txt — `scope`, `verdict`, `severity`, `confidence`, `id` имеют единые значения для всех файлов сессии. `scope` устанавливается в R1 и не меняется между раундами одной сессии.

**Правила для путей в JSON-полях:** только прямые слеши `/`. Обратные слеши ломают JSON-парсер.

**Контракт качества** для reviewer-а уже зафиксирован в `reviewer-prompt.txt` (Шаг 5) и не дублируется в каждом round-start. Если в конкретном раунде нужно усилить какое-то правило — записать в секцию `Особые замечания`.

**Секция `Файлы`:** пути относительно `PROJECT_ROOT`. Для worktree это пути внутри worktree.

### Шаг 4. Запустить reviewer

Сказать пользователю (с подставленными реальными значениями `SESSION_ID`, `SESSION_DIR_ABS`, `REVIEWER_PROMPT_PATH`):

> **Передайте выбранному проверяющему:**
> ```
> Прочитай <REVIEWER_PROMPT_PATH>. При выполнении всех шагов заменяй:
>   {{SESSION_ID}}  →  <session_id>
>   {{SESSION_DIR}} →  <session_dir_abs>
>   {{ROUND_ID}}    →  R1
> ```

Все три плейсхолдера обязательны. Пути — абсолютные с прямыми слешами (`c:/1C/...`). Проверяющий разрешает их без `WT_PREFIX`-логики.

Затем запустить ожидание review-файла через один из скриптов из `SKILL_DIR`. На Windows:

```
description: "Ожидание R1-03-codex-review.md в dual-review сессии <session_id>"
persistent: false
timeout_ms: 1800000
command:
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<SKILL_DIR>/wait-for-review.ps1" -SessionDir "<abs_session_dir>" -RoundId R1 -WaitFor review -TimeoutSec 1800
```

На macOS/Linux или в Git Bash:

```text
command:
  bash "<SKILL_DIR>/wait-for-review.sh" "<abs_session_dir>" R1 review 1800
```

Запустить выбранную команду через доступный механизм длительного ожидания с внешним тайм-аутом не короче 30 минут. Скрипт сам делает адаптивные паузы и возвращает компактный JSON-статус: `{"status":"ready","wait_for":"review","round":"R1","path":"...","elapsed_sec":17}` при появлении файла или `{"status":"timeout",...}` при истечении лимита.

Завершить ход. Когда Monitor выведет JSON со `status: ready` — перейти к Шагу 5. Если `status: timeout` — сообщить пользователю о превышении лимита ожидания и предложить возобновить выбранного проверяющего с тем же `SESSION_ID`.

### Шаг 5. Обработать результат раунда

При получении уведомления о завершении фонового ожидания (или если пользователь явно сообщил, что проверяющий ответил):

1. Перейти в каталог `<SESSION_DIR>`.
2. Найти раунд `RN` с наибольшим `N`, у которого уже есть `RN-03-codex-review.md`, но ещё нет `R<N+1>-01-round-start.md`, и сессия ещё не завершена через `final.md`.
3. Убедиться, что `<SESSION_DIR>/RN-03-codex-review.md` реально существует. Если файл не найден — сообщить пользователю, что review-файл не появился, и предложить возобновить выбранного проверяющего с тем же `SESSION_ID`, `SESSION_DIR` и `ROUND_ID`. После этого завершить ход.
4. Если `RN-04-claude-claimed.flg` уже существует — трактовать это как recovery после прерывания и продолжить обработку этого же раунда.
5. Если `RN-04-claude-claimed.flg` ещё нет — создать его в `<SESSION_DIR>` в самом конце Шага 5, после успешного парсинга и публикации итога. Это означает «раунд обработан», а не «начали читать».
6. Прочитать `<SESSION_DIR>/RN-03-codex-review.md`. Извлечь JSON-блок:

```powershell
$content = Get-Content $reviewFile -Raw
if ($content -match '(?s)```json\s*(.*?)\s*```') {
    $review = $Matches[1] | ConvertFrom-Json
} else {
    throw "JSON-блок не найден в $reviewFile"
}
```

Регулярка выделяет всё содержимое между fence-маркерами (closing ` ``` ` достаточно уникален), без попытки балансировать фигурные скобки. Аналогичная логика в Bash — `awk '/^```json/{flag=1;next}/^```/{flag=0}flag'` или `python -c "import re,sys; m=re.search(r'```json\s*(.*?)\s*```', sys.stdin.read(), re.S); print(m.group(1))"`.

`$review.verdict`, `$review.scope`, `$review.findings` — первичные источники правды. Прозаическая часть ниже JSON-блока — для человека, не для парсинга.

Если JSON-блок отсутствует или невалиден — это восстановимая ошибка протокола. Не перезаписывать `RN-03-codex-review.md` и не пытаться извлечь вердикт из прозы. Если лимит раундов не исчерпан, создать следующий round-start с тем же `scope` и списком файлов, указать в `Особых замечаниях`, что предыдущий JSON был повреждён и материал нужно проверить заново, затем создать `RN-04-claude-claimed.flg` и перейти к ожиданию следующего review-файла. Если лимит исчерпан — создать `final.md` со статусом `failed` и причиной `invalid_review_contract`.

7. Сразу показать пользователю короткий итог раунда:
   - заголовок `**Раунд N**`;
   - `verdict` (из JSON);
   - 1-3 ключевых вывода (из `summary` JSON или `## Краткий вывод` прозаической части);
   - что принято, что отклонено и что меняется дальше (по полю `findings`).
   - итог раунда должен быть сразу видим в чате; не прятать его в `<details>`, сворачиваемый блок или другой скрывающий контейнер.
8. После публикации итога раунда не ждать реакции пользователя и сразу перейти к Шагу 6 в этом же ходе.

### Шаг 6. Верифицировать замечания

Перебрать `$review.findings` по `id`. Для каждого finding зафиксировать одну из трёх позиций:
- `ACCEPTED`
- `REJECTED`
- `INLINE FIX`

Правила:
- `ACCEPTED` — объяснить, почему проблема реальна, и что именно меняется;
- `REJECTED` — дать аргумент: файл, метод, логика;
- `INLINE FIX` — допустим только для локального исправления без смены контракта и архитектуры, но всё равно должен быть отражён в следующем раунде.

Замечания вне текущей области ревью (`scope` отличается от текущего) — `REJECTED`.

Каждое замечание трактовать как гипотезу, а не как команду.

Перед открытием следующего раунда:
- сначала реально внести принятые изменения в план, код и документы, которые будут перечислены в следующем `## Файлы`;
- если замечание принято по plan-файлу, обновить сам plan-файл, а не только описать это в `R<N+1>-01-round-start.md`;
- `Что изменилось с прошлого раунда` описывает только уже внесённые изменения, а не обещания или намерения;
- в `Accepted Issues` / `Rejected Issues` следующего round-start ссылаться на finding по `id` (`F<id>`) и одной строкой описывать решение. Не цитировать прозу замечания — она уже есть в `R<N>-03-codex-review.md`.

### Шаг 7. Следующий раунд или финал

Если `verdict == "APPROVED"` — создать:

```text
<SESSION_DIR>/final.md
```

Шаблон:

```md
# Dual Review Result

## Статус
approved

## Итог
Короткий итог по сессии.
```

Если `verdict == "REJECTED"` — создать:

```text
<SESSION_DIR>/final.md
```

Шаблон:

```md
# Dual Review Result

## Статус
failed

## Причина
Reviewer отказал в продолжении ревью или указал на фундаментальную проблему подхода.
```

Если `verdict != "APPROVED"` и номер текущего раунда достиг `max_rounds` — создать:

```text
<SESSION_DIR>/final.md
```

Шаблон:

```md
# Dual Review Result

## Статус
limit

## Итог
Достигнут лимит раундов. Перечень оставшихся разногласий: ...
```

Если `verdict == "NEEDS_WORK"` и лимит раундов не исчерпан — создать следующий файл:

```text
<SESSION_DIR>/R<N+1>-01-round-start.md
```

Использовать единый шаблон round-start из Шага 3, добавив условные секции `Что изменилось с прошлого раунда`, `Accepted Issues`, `Rejected Issues`. Значение `scope` в JSON-блоке копируется из предыдущего раунда (область ревью не меняется в пределах одной сессии).

После создания нового раунда проверяющий подхватит его автоматически — он уже ждёт появления `R<N+1>-01-round-start.md` в цикле ожидания (Шаг 8 reviewer-prompt.txt). Повторно передавать промпт пользователю не нужно.

Запустить ожидание следующего review-файла тем же скриптом, который был выбран для первого раунда. На Windows:

```
description: "Ожидание R<N+1>-03-codex-review.md в dual-review сессии <session_id>"
persistent: false
timeout_ms: 1800000
command:
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<SKILL_DIR>/wait-for-review.ps1" -SessionDir "<abs_session_dir>" -RoundId R<N+1> -WaitFor review -TimeoutSec 1800
```

Для Bash:

```text
command:
  bash "<SKILL_DIR>/wait-for-review.sh" "<abs_session_dir>" R<N+1> review 1800
```

Подставить реальный `SESSION_DIR` и номер раунда. Когда команда вернёт JSON со `status: ready` — перейти к Шагу 5.

Во всех финальных ветках после записи `<SESSION_DIR>/final.md` сразу показать пользователю короткое видимое сообщение:
- заголовок `**Итог Dual Review**`;
- финальный статус `approved`, `failed` или `limit`;
- 1-3 общих вывода по всей сессии;
- для `failed` или `limit` — главный блокер или оставшееся разногласие.

Недостаточно писать только `Протокол завершён`. После публикации `**Итог Dual Review**` завершить ход.
